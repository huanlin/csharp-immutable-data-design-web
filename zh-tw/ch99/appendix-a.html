附錄 A　開源點字專案的不可變設計重構實戰

最近更新日期

2026-09-12

本附錄改編自開源點字轉換專案 BrailleToolkit 的重構歷程。它不是要示範「把所有 class 改成 record」，而是示範一個更常見、更棘手的情境：既有系統已經有可變模型、UI 編輯器、序列化格式、Undo/Redo、效能熱路徑，這時要怎麼把不可變資料設計安全地導入進去。

這個案例的核心結論是：

不可變設計的價值，不是消滅所有 mutation，而是迫使你說清楚資料的生命週期：哪些資料載入後只查詢，哪些資料仍在建構中，哪些資料必須保留相容性，哪些地方需要明確的 identity。

A.1　專案背景

BrailleToolkit 的工作是將一般文字轉換為點字。中文字與全形標點符號使用台灣點字規則，英文與半形標點符號使用 UEB。轉換流程中有大量查表、字詞建構、後處理規則與文件排版，因此很適合觀察不可變資料設計在真實程式中的取捨。

重構前，系統有幾個典型壓力：

  • 對照表使用 DataTable 載入 XML，轉換熱路徑中大量呼叫 Select(...)。
  • BrailleWord、BrailleLine、BrailleDocument 對外暴露可變集合，呼叫端可以直接插入、刪除或替換內容。
  • 轉換規則、formatter、editor UI 與 Undo/Redo 都假設同一批物件會被持續原地修改。
  • 編輯器狀態依賴 CLR 物件參考來追蹤特定 word 或 line。
  • JSON、YAML 與 clipboard 格式都需要維持相容。

如果一開始就把核心型別全面改成不可變 record，會同時打破太多流程。這次重構採取的是漸進策略：先找出資料生命週期最清楚、效益最大的地方，再逐步收斂 mutation surface。

A.2　總體結果與 Benchmark 方法

效能相關重構不能只靠直覺。這次比較使用 clean worktree A/B benchmark：baseline 與 candidate 分別在乾淨 worktree 中 restore、build、執行 BenchmarkDotNet。baseline 當時尚未有 benchmark 專案，因此只補入相同 benchmark harness；harness 不修改 baseline production code。

比較精準的結論是：

  • DataTable 到 immutable entry + frozen index，是記憶體配置與中文路徑改善的主因。
  • builder / view / result 的分層，讓後續 model 重構能持續推進，且沒有留下 branch-level regression。
  • readonly record struct、builder、with、read-only facade 都不是效能保證；它們只是設計工具，效果必須量測。

A.3　從 DataTable 到 FrozenDictionary

第一個重構切入點，是 XML 點字表查詢。

舊架構使用 DataTable 儲存 XML 載入後的資料，查詢時常見形狀如下：

string filter = "type='Phonetic' and text='" + text + "'";
DataRow[] rows = m_Table.Select(filter);
if (rows.Length > 0)
    return rows[0]["code"].ToString();
return null;

這段程式有幾個問題。DataTable 是很通用、也很重的容器；Select(...) 每次都要解析 filter 字串；查詢條件還要處理 escaping。對大量查表的轉換流程來說，這些成本會反覆出現在熱路徑。

但點字表有一個很關鍵的生命週期特徵：

載入 XML
建立查詢資料
之後大量查詢，不再修改

這正是 immutable entry 與 frozen lookup 適合的位置。

現行程式碼新增了 BrailleTableEntry：

public readonly record struct BrailleTableEntry(
    string Text,
    string Dots,
    string Code,
    string? Type = null,
    string? Dots2 = null,
    string? Code2 = null,
    bool Joined = false,
    bool Mono = false,
    string? Rule = null,
    string? Description = null);

來源：text-to-braille/src/BrailleToolkit/Data/BrailleTableEntry.cs

XmlBrailleTable 則改用 XDocument 解析 XML，載入時直接轉成 BrailleTableEntry[]，再建立三組索引：

private FrozenDictionary<string, BrailleTableEntry> m_EntriesByText;
private FrozenDictionary<BrailleTableLookupKey, BrailleTableEntry> m_EntriesByTypeAndText;
private FrozenDictionary<string, BrailleTableEntry[]> m_EntriesByType;

來源：text-to-braille/src/BrailleToolkit/Data/XmlBrailleTable.cs

這裡其實還有一個值得注意的「建構期可變、完成後 freeze」細節。現行 production code 在 BuildIndexes 中，先使用可變 Dictionary 累積索引：

var entriesByText =
    new Dictionary<string, BrailleTableEntry>(StringComparer.Ordinal);

var entriesByType =
    new Dictionary<string, List<BrailleTableEntry>>(StringComparer.Ordinal);

迴圈完成後，才轉成 FrozenDictionary。這種做法並不違反不可變設計：可變集合只存在於受控的建構階段，離開 BuildIndexes 之前就轉成唯讀查詢結構。

如果專案升級到 C# 15，這段 builder 初始化也可以使用 collection expression arguments。with(...) 必須放在 collection expression 的第一個元素，並把 comparer 等參數傳給目標集合的建構式。例如：

Dictionary<string, BrailleTableEntry> entriesByText =
[
    with(StringComparer.Ordinal)
];

Dictionary<string, List<BrailleTableEntry>> entriesByType =
[
    with(StringComparer.Ordinal)
];

接下來仍然可以在迴圈中呼叫 TryAdd、Add 等方法，最後再 freeze：

m_EntriesByText =
    entriesByText.ToFrozenDictionary(StringComparer.Ordinal);

m_EntriesByType =
    frozenEntriesByType.ToFrozenDictionary(StringComparer.Ordinal);

這項 C# 15 語法沒有改變資料生命週期，也不會讓 Dictionary 自動變成 immutable。它只是讓「這個建構期集合需要使用哪個 comparer」可以直接寫在 collection expression 裡。真正重要的設計仍然是：mutation 被限制在初始化階段，而對外保存的是完成後的 frozen lookup。

C# 版本說明： 上面的 collection expression arguments 是 C# 15 preview 語法；本附錄保留原始 production code 的歷史寫法，這裡只示範升級到 C# 15 後可以採用的等價初始化方式。

查詢變成 domain-specific lookup：

BrailleTableEntry? entry = FindEntry(text, "Phonetic");
return entry?.Code;

Phase 3 單獨的 clean worktree A/B 顯示，這個階段對中文與混合內容改善特別明顯，記憶體配置也大幅下降。

A.4　為什麼不能全部改成 record

BrailleCell 很適合改成 value object。它只包一個 byte，語意上代表一個點字方，因此可以改成 readonly record struct。

但 BrailleWord 與 BrailleLine 不一樣。它們不只是資料容器，也牽涉到既有 editor workflow：

  • formatter 會切行、縮排、插入或移除 word。
  • braille rules 會替換數字符號、補英文大寫符號、處理分數與表格線。
  • editor grid 需要知道某個畫面格子對應哪個 word。
  • Undo/Redo 會複製文件，再還原 selection。
  • JSON、YAML 與 clipboard 格式必須能 round-trip。

如果直接把 BrailleWord / BrailleLine 全部改成 immutable record，每個規則都要改成「輸入舊值、回傳新值」，而且整條呼叫鏈都必須接住新物件。這會牽動太多流程，也很容易在 editor 狀態與序列化相容性上出錯。

所以這次重構選擇了比較務實的分層：

型別 重構策略
BrailleCell 改成小型 readonly record struct
BrailleTableEntry 新增為 immutable lookup entry
BrailleWord 保留 mutable class，新增 view / builder / result / construction boundary
BrailleLine 保留 mutable class，新增 view / builder / result / 明確 mutation API
BrailleDocument 對外公開 read-only facade，內部保留相容所需的 collection

這個策略的重點是：先把任意可變性收斂到少數可理解的位置，而不是假裝整個系統已經準備好完全 immutable。

A.5　公開 API 先改成 read-only facade

重構前，BrailleLine.Words 是公開 List<BrailleWord>。任何呼叫端都能直接：

brLine.Words.Insert(index, word);
brLine.Words.RemoveRange(index, count);
brLine.Words.Add(word);

這讓 mutation surface 太大。你無法只看 BrailleLine 本身，就知道有哪些流程會改它。

重構後，Words 對外改成 IReadOnlyList<BrailleWord>，並補上明確 mutation API，例如 AddWord(...)、InsertWords(...)、RemoveRange(...)、AssignWords(...)。BrailleDocument.Lines 與 BrailleDocument.PageTitles 也採取類似做法。

這不是完整的 immutable collection。IReadOnlyList<T> 只是 read-only facade，底層仍可能是可變集合。但它是重要的中間步驟：

  • 外部呼叫端不能隨手修改集合。
  • 修改入口變少，後續可以逐一審查。
  • 序列化與 editor 相容性比較容易維持。
  • 測試可以針對明確 mutation API 補強。

這一步看起來不像華麗的語言特性，但對大型既有系統很關鍵。先縮小修改入口，才有機會談更深的不可變設計。

A.6　Builder Boundary：建構期可變，完成後可讀

接下來是 BrailleWord 與 BrailleLine 的 Builder Boundary。

BrailleWord 新增了幾個內部角色：

IBrailleWordView
IBrailleWordResult
BrailleWordBuilder
BrailleWordMaterialized
BrailleWord

IBrailleWordView 是唯讀檢視。helper、formatter、font converter 只需要讀資料時，可以依賴這個介面，而不是直接依賴可變 class。

以下是省略 metadata 後的概念化摘要：

internal interface IBrailleWordView
{
    string Text { get; }
    string OriginalText { get; }
    BrailleLanguage Language { get; }
    int CellCount { get; }
    BrailleCell GetCell(int index);
}

BrailleWordBuilder 則負責建構階段的 mutation。現行 source 使用 BrailleCellBuffer 管理 cell sequence，並支援從既有 BrailleWord 載入狀態、建立 materialized result，或套回既有 word。

以下是依現行 source 簡化後的摘要：

internal sealed class BrailleWordBuilder
{
    private BrailleCellBuffer _cells;

    public string Text { get; set; }
    public string OriginalText { get; set; }
    public BrailleLanguage Language { get; set; }

    public static BrailleWordBuilder FromBrailleWord(BrailleWord source)
    {
        var builder = new BrailleWordBuilder(source.Text)
        {
            OriginalText = source.OriginalText,
            Language = source.Language
        };

        builder.AppendCells(CollectionsMarshal.AsSpan(source.Cells));
        return builder;
    }

    public IBrailleWordResult Build()
    {
        return new BrailleWordMaterialized
        {
            Text = Text,
            OriginalText = OriginalText,
            Language = Language,
            Cells = _cells.ToArray()
        };
    }

    public void ApplyTo(BrailleWord target)
    {
        target.ApplyConstruction(
            Text,
            OriginalText,
            Language,
            _cells.AsSpan());
    }
}

來源：text-to-braille/src/BrailleToolkit/BrailleWordBuilder.cs

這個 builder 有兩個重要用途。

第一，它可以建立新的結果：

IBrailleWordResult result = builder.Build();
BrailleWord word = builder.ToBrailleWord();

第二，它可以套用到既有 word：

var builder = BrailleWordBuilder.FromBrailleWord(existingWord);
builder.PrependCell(BrailleCell.Capital);
builder.ApplyTo(existingWord);

這對既有規則很重要。很多 braille rule 不是單純建立新 word，而是在轉換後替既有 word 補 cell、換 cell 或加 metadata。FromBrailleWord(...).ApplyTo(...) 讓 mutation 集中在 construction boundary，同時保留舊流程需要的物件相容性。

BrailleLineBuilder 採取同樣策略：建構階段可以 AddWord(...)、InsertWords(...)、RemoveContextTags()；完成後可以 Build() 成 result，也可以 ToBrailleLine() 或 ApplyTo(...) 進入仍需要可變模型的流程。

這個設計並沒有承諾「每一步都更快」。它的價值是讓可變性出現在可命名、可測試、可量測的位置。

A.7　Explicit Identity：不要把物件參考當成模型識別

一旦系統開始使用 builder、copy、materialized result、JSON/YAML round-trip，原本依賴 ReferenceEquals 的邏輯就會變得脆弱。

例如，文件中可能有兩個內容完全相同的 BrailleWord。值相等不代表它們是同一個位置的 word。editor selection、Undo/Redo、page title anchor 需要追蹤的是「這一個資料個體」，而不是「內容一樣的資料」。

現行 BrailleWord 與 BrailleLine 因此加入 runtime identity：

public sealed class BrailleWord : IBrailleWordView
{
    private long m_Identity = BrailleObjectIdentityGenerator.NextWordIdentity();

    public long Identity
    {
        get { return m_Identity; }
    }
}

BrailleObjectIdentityGenerator 使用 Interlocked.Increment(...) 發號：

internal static class BrailleObjectIdentityGenerator
{
    private static long s_NextWordIdentity;
    private static long s_NextLineIdentity;

    public static long NextWordIdentity()
    {
        return Interlocked.Increment(ref s_NextWordIdentity);
    }

    public static long NextLineIdentity()
    {
        return Interlocked.Increment(ref s_NextLineIdentity);
    }
}

來源：

  • text-to-braille/src/BrailleToolkit/BrailleWord.cs
  • text-to-braille/src/BrailleToolkit/BrailleLine.cs
  • text-to-braille/src/BrailleToolkit/BrailleObjectIdentityGenerator.cs

BrailleLine.IndexOf(BrailleWord) 也改成用 word identity 比對，而不是依賴物件參考。editor 的 grid bookmark、selection restore、page title anchor 也可以用 line / word identity 找回目前文件中的位置。

這裡的重點不是把 runtime identity 當成 domain ID 存進外部資料庫。它是 editor runtime 裡的穩定追蹤機制，用來取代「剛好同一個 CLR object」這種太脆弱的假設。

A.8　序列化與相容層

read-only facade 與 builder boundary 導入後，序列化也要一起處理。

JSON / DataContract 方面，BrailleLine.Words 對外可以是 read-only facade，但序列化格式仍需要維持既有 Words 欄位。做法是保留 backing field，並讓公開屬性避開 DataContract：

[DataMember(Name = "Words")]
private List<BrailleWord> m_Words;

[IgnoreDataMember]
public IReadOnlyList<BrailleWord> Words
{
    get { return m_Words; }
}

YAML 則改用 DTO model round-trip。serialize 時從 read-only view 讀取資料，deserialize 時透過 builder 或 construction boundary 建回 runtime model。

這樣做的好處是：runtime model 可以逐步收斂 mutation surface，但外部資料格式不必跟著劇烈震盪。對有真實使用者資料的應用程式來說，這類相容層不是附屬品，而是重構設計的一部分。

A.9　這次重構真正教會我們的事

這個案例最後留下幾個判斷原則。

第一，先釐清生命週期，再選資料結構。載入後大量查詢、不再修改的資料，適合 immutable entry 加 frozen lookup；建構中的資料，使用 builder 反而更自然。

第二，IReadOnlyList<T> 不是 immutable collection，但它可以先把公開 mutation surface 收斂起來。這在既有系統中非常有用。

第三，value type 不保證更快。BrailleCell 改成 readonly record struct 讓語意更正確，但 Phase 4a 曾經出現 throughput regression。效能結論必須靠 benchmark，不應靠語感。

第四，Builder Boundary 的目標不是讓每個中間步驟看起來「純函數式」，而是把可變性集中到能測試與量測的地方。

第五，當系統需要追蹤 UI selection、Undo/Redo、page title anchor 或特定資料個體，不要依賴 ReferenceEquals。導入 copy、builder 或序列化重建之前，先設計 explicit identity。

第六，重構不是只改型別。它通常會同時牽動 benchmark、測試、序列化、相容層與文件。真正成熟的不可變資料設計，是一組工程取捨，而不是單一語法特性。

結語：不可變資料設計是一種取捨
