前言：為什麼需要不可變資料設計

最近更新日期

2026-09-13

你有沒有遇過這種情況：測試突然失敗，找了半小時才發現是某個方法改了一個物件的狀態，而那個物件還有其他物件正在使用？

或這種情況：你追一個 bug 追了很久，最後發現問題不在你懷疑的那段程式碼，而是某個物件在傳遞過程中被一些程式碼修改了，而你一直都不知道其實很多地方都會改變那個物件的狀態。

又或者這種情況：你的 Web API 收到一個 HTTP 請求，請求內容被轉成一個 request DTO；你需要把它轉換成領域物件，再轉成資料庫用的實體物件，之後再轉成 response DTO。在此過程中，每一層都使用不同的類別，每一層的物件都可能在你沒發現的地方被修改。

備註：這裡的 DTO 是 data transfer object（資料傳輸物件）的縮寫。request DTO 承載外部請求的資料，response DTO 則承載 API 回應資料。

圖：從 HTTP 請求到回應的物件流動過程。當每一層都能修改物件狀態時，資料來源與修改責任會變得越來越難追蹤。

HTTP Request
     |
     | 反序列化 / Model Binding
     v
Request DTO
     |
     | 轉換
     v
Domain Object
     |
     | 套用規則 / 業務流程
     v
Persistence Entity
     |
     | 儲存 / 查詢 / 重新組裝
     v
Response DTO
     |
     | 序列化
     v
HTTP Response


在流程中可能發生的事：

Request DTO        可能被修改
Domain Object      可能被修改
Persistence Entity 可能被 ORM 或程式碼修改
Response DTO       可能來自已被改過的狀態

結果：
「資料現在是什麼值？」
「是誰改的？」
「在哪一層改的？」
「這個物件還能不能信任？」

圖中的 Domain Object 是用來表達核心業務概念與規則；Persistence Entity 則是配合資料庫或資料存取工具使用的儲存模型。這只是常見的責任分工，不表示每個系統都必須使用不同型別或採用特定的分層架構。

這些場景有一個共同的根源：可變狀態（mutable state）在程式中流動，讓你很難確定資料在某個時間點究竟是什麼值、是誰改的、在哪裡改的。

本書欲探討和解決的正是這個問題。

不是銀彈

這本書不是「放棄物件導向（OOP）」的書。物件導向有它的強項與適合場景：封裝複雜的業務規則、管理有生命週期的實體、維護物件在任何時候都必須滿足的規則。這些場景仍然需要物件導向的封裝。

這也不是一本講函數式程式設計（functional programming）的書。我們不會把全部的 C# 程式碼改成只有熟悉函數式風格才看得懂的資料轉換管線，也不會假裝你不用和「物件-關聯對應」工具（ORM，例如 Entity Framework Core）打交道。

這本書想要講的是一個務實的觀點：

C# 近年來加入了許多語言特性，使得「讓資料保持透明、不可變、可追蹤」變得容易許多。問題是，很多開發者知道這些語法，卻不知道它們組合在一起能帶來什麼樣的設計改變。

C# 的 record、init、with、ImmutableList<T>、switch 運算式——這些特性不只是個別的語法或 API，更是一套能用來建構不可變資料模型的工具組。本書的目的，就是讓你知道如何善用這套工具組來改善軟體的設計，而不是只看一些語法範例。

這本書要解決什麼問題

想像一個訂單系統。訂單建立之後，可以被提交、付款、出貨，也可以被取消。如果用傳統的可變物件設計，整個訂單物件的狀態通常會在處理流程中的某些地方修改相關屬性，例如：

order.Status = OrderStatus.Paid;
order.PaidAt = DateTime.Now;
order.UpdatedBy = currentUser;

這樣寫當然能跑。但隨著程式規模擴大，問題就來了：

  • 你要追蹤「是誰、在哪裡、在什麼條件下」把 Status 從 Submitted 改成 Paid，變得非常困難。
  • 如果一個方法接收了 order 並在內部改了某個欄位，你只能靠閱讀程式碼（而不是型別簽名）才能發現這件事。
  • 測試這個流程時，你必須小心管理物件的初始狀態，否則不同測試之間可能互相干擾。

不可變設計的做法是：每次狀態改變，都產生一個新的訂單版本，不會動到舊的版本。像這樣：

var paidOrder = order.MarkAsPaid(clock.Now);

paidOrder 是一個新物件，原本的 order 保持不變。這樣做的好處是：你可以隨時知道某個版本的訂單在那個時間點的完整狀態。

其背後的思維是務實的工程決策：把「原地修改同一個物件的狀態」這件事改成一種「資料轉換」的形式。這樣的程式更容易測試、更容易追蹤，也比較容易在多執行緒或非同步流程中安全共享資料——因為原本的物件不會被修改，其他程式碼即使同時讀取它，也不必擔心資料在中途被改掉。第 5 章會說明這項好處的適用範圍與限制。

本書架構

本書分為六章，以訂單處理系統作為貫穿全書的主要範例。之所以選擇訂單系統，是因為它同時具備了大多數設計挑戰：狀態轉換、API 輸入輸出資料、集合、驗證、資料持久化，以及狀態建模。

第 1 章從最基本的問題切入：為什麼可變物件在小程式裡方便，卻在大型程式中帶來追蹤困難？本章的功能是建立全書主旨：不要直接改掉同一個物件，而是把每一次改變表達成「從舊版本建立新版本」。

第 2 章介紹 C# 中用來建構不可變資料的語言特性：record class、record struct、init、required、with 運算式，以及不可變集合的選擇指南。這章是工具箱章節，會特別強調一個常見陷阱：用了 record 並不代表資料真的不可變。

第 3 章是全書核心。本章會討論「用資料轉換取代原地修改」究竟意味著什麼，以及在行為邏輯放在型別內還是放在外部服務之間，如何做出實務上的判斷。讀完這章，你應該能看懂不可變設計在業務流程中的實際寫法。

第 4 章把討論重心從領域模型（domain model）轉向 Web API 與其他資料傳輸情境，探討 request/response DTO、System.Text.Json 整合、validation 的位置選擇、DTO 與 domain model 的分離，以及 command object 和 event payload，並說明不可變設計為何容易在這些位置落實。

第 5 章總結全書的核心內容：不可變資料在哪些位置最容易產生效益，又會帶來哪些成本？本章會釐清可追蹤性、測試與並行讀取的適用範圍，並討論封裝、物件配置、深層更新、物件-關聯對應（ORM）、序列化、UI 資料繫結與強封裝物件。最後會提供漸進導入的順序和決策參考表，幫助你判斷何時該採用可變設計。

第 6 章是進階選讀。當 enum、旗標與 nullable 欄位已經讓非法狀態難以避免時，可以進一步用狀態型別和 pattern matching 建模。若第 3 章的單一 Order record 已經足夠清楚，可以略過這章。

目標讀者

這本書適合你，如果你：

  • 已經會寫 C#，熟悉類別（class）、介面（interface）、LINQ、async/await 基礎觀念。
  • 知道 record 這個關鍵字，但不確定什麼時候該用。
  • 在設計 API 的 request DTO 與 response DTO 時，會在可變 class、record、readonly struct 之間猶豫。
  • 知道不可變資料很好，但實務上不知道怎麼更新深層嵌套的資料。
  • 聽過不可變設計，但不確定跟你目前的 C# 專案有什麼關係。

這本書假設你有中階的 C# 開發經驗。我們不會從頭解釋什麼是類別或介面，但也不會預設你熟悉進階的型別理論或 functional programming 的術語。

技術環境

本書的程式碼範例以 C# 14 和 .NET 10 為基準，但絕大多數內容在 C# 10（.NET 6）以上就能適用。

使用較新的語法時，會說明該特性是從哪個版本開始可用，以及在舊版本中的替代做法。

開始之前

為了避免誤解，這裡先釐清一件事：本書不會告訴你「所有東西都改成 record 就對了」，也不會說「把方法全部搬到服務類別（service class）裡就是好的設計」。

實際上，這本書的一個主要目的，是希望幫你建立一種判斷力：看到一段程式碼或一個設計問題時，能夠判斷這裡適不適合用不可變設計（immutable design）；如果適合，又該怎麼做。

這種判斷能力通常比背誦一堆教條更有用。
