第 3 章　用資料轉換取代原地修改

最近更新日期

2026-09-12

本章內容：

  • 什麼是「資料轉換（data transformation）」
  • 風格 A：把行為放在 record 內部
  • 風格 B：把行為放在外部函式或服務
  • 兩種風格的比較與預設選擇建議
  • 轉換管線（transformation pipeline）的概念
  • 失敗處理和轉換管線的實務做法

本章是全書的核心。

前兩章建立了基礎：第 1 章介紹了「改變 = 建立新版本」的思維，第 2 章介紹了 C# 裡用來建構不可變資料的工具。現在，我們要回答一個更實際的問題：

當你的程式需要「更新」一筆資料時，這個邏輯應該放在哪裡？

這裡說的「更新」，不是直接修改既有物件，而是第 1 章介紹過的資料轉換：接收舊狀態，回傳新狀態。換句話說，本章關心的不是「如何讓物件被改掉」，而是「如何把狀態前進這件事設計成清楚、可測試、可維護的轉換」。

這個問題沒有一個放諸四海皆準的答案。本章會提供一組實務判斷準則，幫助你思考幾個問題：

  • 這筆資料是 domain model 還是 DTO？（3.3 節）
  • 狀態轉換是否需要維護業務規則？（3.4 節）
  • 操作是否依賴資料庫、時間、或外部服務？（3.6 節）

答案不同，更新邏輯適合放的位置也會不同。

3.1　可變更新 vs 不可變轉換

在討論更新邏輯應該放在哪裡之前，本節先快速複習第 1 章提過的核心觀念：可變設計會直接修改既有物件；不可變設計則把改變表達成「接收舊狀態，回傳新狀態」的資料轉換。

想像訂單系統的付款流程。使用可變設計時，你可能這樣寫：

// 可變更新（mutable update）
public void MarkAsPaid(Order order, DateTimeOffset paidAt)
{
    order.Status = OrderStatus.Paid;
    order.PaidAt = paidAt;
}

這個方法直接修改了傳進來的 order。由於呼叫方的 order 物件在方法執行後已經變了，這種對傳入物件的原地修改就是副作用（side effect）的一種。

Note: 簡單來說，「副作用」是指方法透過回傳值以外的方式，造成呼叫方可以觀察到的狀態變化或外部互動，例如修改傳入物件或共享狀態、寫入資料庫、或輸出訊息。

使用不可變設計時，同樣的邏輯可以改成：

// 不可變轉換（immutable transition）
public Order MarkAsPaid(Order order, DateTimeOffset paidAt)
{
    return order with
    {
        Status = OrderStatus.Paid,
        PaidAt = paidAt
    };
}

這個方法回傳一個新物件，不修改輸入的 order。呼叫方需要使用回傳值。以下範例以 .NET 內建的 TimeProvider 取得目前時間；第 3.6 節會完整說明這個時間抽象：

var paidAt = timeProvider.GetUtcNow();

// 可變版本的呼叫方式（會修改 order）
orderService.MarkAsPaid(order, paidAt);
// order 已經被改了，但從程式碼看不出來

// 不可變版本的呼叫方式（回傳新物件）
var paidOrder = orderService.MarkAsPaid(order, paidAt);
// order 沒有改變，paidOrder 是新的版本

不可變版本的回傳型別會提醒呼叫方：這個方法會回傳一個 Order，請把它視為新版本。不過，C# 的方法簽名本身無法保證實作沒有同時修改輸入；這仍須由型別設計與方法實作共同確保。

第 1 章補充說明過，即使將參數宣告為 in Order order，對參考型別來說，也只能防止方法重新指派 order 這個參數，不會讓它指向的物件自動變成不可變。

3.2　兩種設計風格

「把改變表達成轉換」這個思維有兩種常見的實作風格，各有優缺點。第 1 章的 OrderWorkflow 範例其實已經示範了其中一種：把轉換邏輯放在 Order 外部。這一節會先把兩種寫法並排放在一起，接著再討論它們各自適合什麼情境。

風格 A：行為放在 record 內部

這種作法類似傳統 OOP 的設計，由 record 本身提供轉換方法，但這些方法不會修改 this（物件本身），而是回傳新版本。為了聚焦在這個封裝方式，下面的範例只保留建立草稿和提交訂單所需的屬性：

public sealed record Order
{
    public OrderStatus Status { get; private init; }
    public ImmutableArray<OrderLine> Lines { get; private init; }
    public DateTimeOffset CreatedAt { get; private init; }
    public DateTimeOffset? SubmittedAt { get; private init; }

    private Order(
        ImmutableArray<OrderLine> lines,
        DateTimeOffset createdAt)
    {
        Status = OrderStatus.Draft;
        Lines = lines;
        CreatedAt = createdAt;
    }

    public static Order CreateDraft(
        ImmutableArray<OrderLine> lines,
        DateTimeOffset createdAt)
    {
        if (lines.IsDefault)
        {
            throw new ArgumentException(
                "訂單項目尚未初始化",
                nameof(lines));
        }

        return new Order(lines, createdAt);
    }
}

這裡刻意使用非位置式 record（而不是 positional record），並將建構式與所有 init 存取子設為 private，因此呼叫方無法繞過轉換方法直接改寫狀態。若要讓訂單進入下一個狀態，就必須透過 Order 提供的轉換方法。例如，Submit 方法會讀取 this，再用 with 建立新版本。

Note: 如果採用常見的 public positional record 寫法，由編譯器產生的 primary constructor 以及根據位置參數產生的屬性都是 public，而且這些屬性都具有 public init 存取子。init 只能防止物件建立後的一般指派，不會禁止呼叫方使用 with 在新版本中設定這些屬性。因此，呼叫方可能繞過 Submit 方法內的驗證邏輯，直接建立一個內容矛盾的版本，像這樣：

var invalid = draft with
{
    Status = OrderStatus.Submitted,
    SubmittedAt = null
};

這個問題的關鍵不是 positional record 語法本身，而是與狀態有關的建構入口和 init 存取子仍對外開放。這裡改用非位置式 record，是為了更明確地限制這些存取點。

接著來看 Order 的狀態轉換方法。為了避免程式碼太過冗長，以下只展示 Submit 方法；其他業務規則會在第 3.4 節說明：

public Order Submit(DateTimeOffset now)
{
    if (Status != OrderStatus.Draft)
    {
        throw new InvalidOperationException(
            "只有草稿可以提交");
    }

    return this with
    {
        Status = OrderStatus.Submitted,
        SubmittedAt = now
    };
}

Lines 也改用 ImmutableArray<OrderLine>，避免外部程式透過原本的 List<OrderLine> 參考修改訂單項目。工廠方法會拒絕處於 default 狀態的 ImmutableArray<OrderLine>，以呼應第 2 章介紹過的集合設計。

完整版本還包含 Pay、Ship、和 Cancel，它們都採用相同的轉換結構。這些方法的名稱像是命令，但實際行為是轉換，所以呼叫方必須接住回傳值。因為每個方法都回傳 Order，呼叫方也可以將它們串接起來：

var now = timeProvider.GetUtcNow();

var shipped = order
    .Submit(now)
    .Pay(now.AddHours(2))
    .Ship(now.AddDays(1));

這種寫法可以流暢地串接（method chaining），看起來很自然。在支援程式碼補全（code completion）的 IDE 中，輸入 . 就能看到這個訂單支援哪些操作。

原始碼： DemoOrderTransformationStyleA

風格 B：行為放在外部函式或服務

另一種作法，是像第 1 章的 OrderWorkflow 那樣，把轉換邏輯放在一個獨立的靜態類別（或服務）裡，讓 Order 本身保持為資料容器：

public sealed record Order(
    string Id,
    string CustomerId,
    OrderStatus Status,
    ImmutableArray<OrderLine> Lines,
    decimal Total,
    DateTimeOffset CreatedAt,
    DateTimeOffset? SubmittedAt = null,
    DateTimeOffset? PaidAt = null,
    DateTimeOffset? ShippedAt = null,
    string? CancelReason = null);

public static class OrderWorkflow
{
    public static Order Submit(Order order, DateTimeOffset now)
    {
        return order with
        {
            Status = OrderStatus.Submitted,
            SubmittedAt = now
        };
    }

    public static Order Pay(Order order, DateTimeOffset now)
    {
        return order with
        {
            Status = OrderStatus.Paid,
            PaidAt = now
        };
    }
}

這種風格的呼叫方式會把目前的訂單版本明確傳進每個轉換函式：

var now = timeProvider.GetUtcNow();
var submitted = OrderWorkflow.Submit(order, now);
var paid = OrderWorkflow.Pay(submitted, now.AddHours(2));

在這個例子裡，Order 不需要知道有哪些操作會改變它；所有業務流程都集中在 OrderWorkflow。這和風格 A 使用的是同一個不可變轉換規則，只是方法的位置不同。為了聚焦在方法的位置，上面的 Submit 和 Pay 暫時省略了狀態驗證；第 3.4 節會補上這些規則。

不過，這個 positional record 仍允許呼叫方自行使用 with；若要確保狀態轉換都經過 workflow，還需要額外的封裝設計，或明確的團隊慣例。

原始碼： DemoOrderTransformationStyleB

這種寫法看起來很接近「貧血模型（anemic domain model）」，值得花點篇幅解釋一下。

所謂貧血模型，通常是指一個 domain model 只有資料欄位，幾乎沒有行為；真正的業務規則散落在 controller、service、UI handler 或 repository 等地方。結果是 Order 看起來像 domain model，但它本身無法保護自己的狀態：任何地方只要拿到訂單，就可能直接把 Status 改成 Paid，卻忘了檢查訂單是否已提交、是否已取消、是否已經付款。問題不只是「方法沒有放在 Order 裡」，而是業務規則沒有被集中、清楚、可靠地表達。

參閱：Martin Fowler, Anemic Domain Model

因此，風格 B 不一定等於壞的貧血模型。關鍵在於轉換規則是否有明確的歸屬。如果 Order 本身保持為資料容器，但所有狀態變化都必須透過 OrderWorkflow.Submit、OrderWorkflow.Pay 這類轉換函式，而且這些函式集中處理業務規則，那麼這比較像是把 domain workflow 放在外部模組中，而不是讓規則散落各處。資料和行為雖然沒有放在同一個型別裡，但它們仍然透過清楚的 API 被組織在一起。

反過來說，如果 Order 只是資料容器，而系統裡到處都可以自由改寫它的狀態，那就會落入貧血模型常見的問題：規則難以追蹤、狀態容易不一致、測試也必須追著各種呼叫路徑跑。風格 B 要成立，前提是團隊必須有清楚的慣例：狀態轉換要集中在 workflow、domain service 或其他目的明確的模組中，而不是散落在每個需要用到訂單的地方。

3.3　兩種風格的比較

以下表格整理了風格 A 與風格 B 在幾個常見面向上的差異：

比較面向 風格 A（行為在 record 內） 風格 B（行為在外部）
IDE 可探索性 輸入 . 可以看到可用操作 需要知道要去哪個類別找
資料透明度 取決於公開 API；本例可讀取資料，但限制呼叫方直接重建所有狀態 高（公開 positional record 可直接重建）
確保狀態合法 比較集中（可以在方法內做驗證） 需要額外設計
測試 容易 容易
適合 DTO 不一定（DTO 通常不需要行為） 較適合
適合 domain model 較適合（有業務規則） 視情況
適合跨分層傳遞資料 不一定 較適合

行為是否定義在 record 內，並不直接決定資料透明度；真正的判斷依據是，公開 API 是否足以讀取並重建其資料內容。

其中的「確保狀態合法」，其實就是「這個物件在任何時候都必須符合的規則」，例如：

  • 已付款訂單必須有付款時間
  • 已取消訂單必須有取消原因
  • 草稿（draft）訂單才能提交
  • 已取消訂單不能再付款

預設建議：從風格 A 開始

如果你不確定用哪種，建議可以從風格 A 開始——把行為放在 record 內部。

理由是：

  • IDE 可探索性（discoverability）更好，新加入的開發者可以透過 . 發現可用操作。
  • 比較容易確保狀態合法；你可以在方法內部做驗證，避免轉換後產生不合理的狀態。
  • 大多數 C# 開發者對這種寫法更熟悉，學習曲線較低。

何時考慮切換到風格 B？

當你遇到以下情況時，外部函式或服務的設計可能更適合：

  • 同一筆資料有多種不同的操作邏輯，而這些邏輯分屬不同的業務領域（例如：訂單的定價邏輯、物流邏輯、財務邏輯各自獨立）。
  • 資料需要跨越系統分層或 API 介面（例如 API request/response DTO），這類資料的角色是「傳遞資訊」，不應該帶著業務邏輯。
  • 操作邏輯需要外部依賴（資料庫、外部服務），把它放在 record 外部的服務中更合適。

記住：兩種風格可以混用。同一個 Order record 可以保留純粹的狀態轉換方法，再由 application service 取得資料庫、時間、或外部服務的結果，並把普通資料傳給這些方法。service 負責協調外部依賴，不代表業務規則也必須跟著移出 domain model。

3.4　加入業務規則驗證

實務上的狀態轉換不只是「更新欄位」，還需要驗證當前狀態是否允許這個轉換。

例如，一張「草稿（draft）」訂單才能被提交，一張「已取消」的訂單不能再付款。這種「從某個狀態才能轉換到另一個狀態」的約束，就是業務規則（business rule）。

拋出例外：簡單直接

最直接的做法是在轉換方法裡驗證，如果不滿足就拋出例外：

public sealed record Order
{
    // ... 屬性與建構式略

    public Order Submit(DateTimeOffset now)
    {
        if (Status != OrderStatus.Draft)
        {
            throw new InvalidOperationException(
                $"只有草稿狀態的訂單可以提交，當前狀態：{Status}");
        }
        if (Lines.Count == 0)
        {
            throw new InvalidOperationException(
                "訂單必須至少有一個項目才能提交");
        }

        return this with
        {
            Status = OrderStatus.Submitted,
            SubmittedAt = now
        };
    }

    public Order Pay(DateTimeOffset now)
    {
        if (Status != OrderStatus.Submitted)
        {
            throw new InvalidOperationException(
                $"只有已提交的訂單可以付款，當前狀態：{Status}");
        }

        return this with
        {
            Status = OrderStatus.Paid,
            PaidAt = now
        };
    }
}

這種做法簡單，但不代表每個呼叫方都必須就地使用 try-catch。如果不合法的轉換代表程式設計錯誤，可以讓例外交由應用程式的統一錯誤處理機制接住；如果它是使用者操作時可預期的結果，下一節的結果型別通常更合適。也不要只在呼叫前重複檢查狀態，因為真正維護規則的地方仍應該是轉換方法。

回傳結果型別：更明確的錯誤處理

另一種做法是讓方法回傳一個結果型別，明確表達「成功」或「失敗」。

同樣以訂單為例，我們可以先定義一個代表轉換結果的型別，名稱是 OrderTransitionResult：

public sealed record OrderTransitionResult
{
    public bool IsSuccess { get; }
    public Order? Order { get; }
    public string? ErrorMessage { get; }

    private OrderTransitionResult(
        bool isSuccess,
        Order? order,
        string? errorMessage)
    {
        IsSuccess = isSuccess;
        Order = order;
        ErrorMessage = errorMessage;
    }

    public static OrderTransitionResult Success(Order order)
    {
        ArgumentNullException.ThrowIfNull(order);
        return new(true, order, null);
    }

    public static OrderTransitionResult Fail(string message)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(message);
        return new(false, null, message);
    }
}

然後，在負責處理訂單流程（workflow）的方法中回傳這個結果型別，而不是在驗證失敗時拋出例外：

public static class OrderWorkflow
{
    public static OrderTransitionResult Submit(
        Order order,
        DateTimeOffset now)
    {
        if (order.Status != OrderStatus.Draft)
        {
            return OrderTransitionResult.Fail(
                $"只有草稿狀態的訂單可以提交，當前狀態：{order.Status}");
        }

        var submitted = order with
        {
            Status = OrderStatus.Submitted,
            SubmittedAt = now
        };

        return OrderTransitionResult.Success(submitted);
    }
}

呼叫方：

var result = OrderWorkflow.Submit(
    order,
    timeProvider.GetUtcNow());

if (!result.IsSuccess)
{
    logger.LogWarning("提交訂單失敗：{Message}", result.ErrorMessage);
    return;
}

var submitted = result.Order!;
await orderRepository.SaveAsync(submitted);

這種做法讓錯誤處理更明確，呼叫方從型別就能看出這個操作可能失敗，比較不容易忽略錯誤情況。

建構式設為 private，並由工廠方法驗證參數之後，呼叫方也不能自行建立「成功但 Order 是 null」這類互相矛盾的組合。不過，C# 的 nullable analysis 仍無法從 IsSuccess 推導 Order 一定有值，所以範例仍需要使用 !。進階選讀的第 6 章會把相同的型別建模思路用在訂單生命週期，讓不同訂單狀態成為不同型別；它不是專門改寫這裡的結果型別。

順便提及，這個思路和 Go 語言的錯誤處理哲學相近：錯誤不是隱藏在例外流程裡，而是作為回傳值的一部分交給呼叫方判斷。

.NET 基礎類別庫目前沒有內建的 Result<TValue, TError> 型別，也就是「成功時回傳 TValue，失敗時回傳 TError」的通用結果型別，但你可以用上面的方式自己定義，或引入 ErrorOr、FluentResults 等第三方套件來獲得更完整的 Result 型別支援。

3.5　轉換管線：把多個步驟串接起來

不可變設計的另一個好處是：因為每個轉換都回傳新物件，多個步驟可以很自然地串接成一條「轉換管線」。

以下範例展示的是風格 A 的串接（method chaining）寫法：

var now = timeProvider.GetUtcNow();

var finalOrder = draft
    .Submit(now)
    .Pay(now.AddHours(2))
    .Ship(now.AddDays(1));

接著是風格 B 的逐步轉換寫法：

var now = timeProvider.GetUtcNow();
var submitted = OrderWorkflow.Submit(draft, now);
var paid = OrderWorkflow.Pay(submitted, now.AddHours(2));
var shipped = OrderWorkflow.Ship(paid, now.AddDays(1));

這兩種寫法都是把狀態轉換組成管線，讓整個業務流程的邏輯一目了然。你不需要在腦子裡追蹤「哪個物件在哪個步驟被改了什麼」，而是清楚地看到一個狀態如何流動轉換成下一個狀態。

這裡先展示每一步成功時的資料流。如果轉換回傳的是上一節的 OrderTransitionResult，下一步就不能直接接收它，而必須先判斷是否成功，再把成功結果裡的 Order 傳下去。更通用的 Result 型別通常會提供 Bind 或 Then 之類的組合操作，讓失敗直接中止後續步驟；無論採用哪種 API，關鍵都是讓上一個步驟的成功輸出成為下一個步驟的輸入。

下圖描繪了資料轉換的管線，圖中的每個方塊代表一個不同的 Order 物件。每一步都接收目前的訂單版本，產生下一個版本；原本的 draft 不會被修改。

+-----------------------+
| Order (Draft)         |
+-----------------------+
            |
            | Submit(...)
            | returns a new Order
            v
+-----------------------+
| Order (Submitted)     |
+-----------------------+
            |
            | Pay(...)
            | returns a new Order
            v
+-----------------------+
| Order (Paid)          |
+-----------------------+
            |
            | Ship(...)
            | returns a new Order
            v
+-----------------------+
| Order (Shipped)       |
+-----------------------+

初次改用這種風格時，最常見的錯誤是忘記接住回傳的新版本：

// 錯誤示範：Submit 回傳的新版本被丟掉了
draft.Submit(timeProvider.GetUtcNow());

// draft 仍然是原本的草稿訂單，因為它沒有被修改

不可變轉換方法不會修改原本的物件，而是透過回傳值提供新的狀態，因此呼叫方必須把回傳值視為新的狀態來源。你可以把它想成一條資料流：每一步都接收上一個狀態，產生下一個狀態；如果中間某一步的輸出被丟掉，流程就中斷了。

在測試中驗證每個步驟

轉換管線的另一個好處是，每一步都可以獨立驗證：

[Fact]
public void Complete_Order_Lifecycle_Should_Produce_Correct_States()
{
    var fixedTime = new DateTimeOffset(
        2026, 1, 1, 10, 0, 0, TimeSpan.Zero);

    // 建立草稿
    var draft = Order.CreateDraft(
        id: "ORD-001",
        customerId: "CUST-42",
        lines: ImmutableArray.Create(
            new OrderLine("P001", "書", 2, 350m)),
        createdAt: fixedTime);

    Assert.Equal(OrderStatus.Draft, draft.Status);
    Assert.Equal(700m, draft.Total);

    // 提交
    var submitted = draft.Submit(fixedTime.AddMinutes(5));
    Assert.Equal(OrderStatus.Submitted, submitted.Status);
    Assert.Equal(fixedTime.AddMinutes(5), submitted.SubmittedAt);

    // 確認 draft 不受影響
    Assert.Equal(OrderStatus.Draft, draft.Status);
    Assert.Null(draft.SubmittedAt);

    // 付款
    var paid = submitted.Pay(fixedTime.AddHours(1));
    Assert.Equal(OrderStatus.Paid, paid.Status);
    Assert.Equal(fixedTime.AddHours(1), paid.PaidAt);

    // 出貨
    var shipped = paid.Ship(fixedTime.AddDays(1));
    Assert.Equal(OrderStatus.Shipped, shipped.Status);
}

這個測試清晰地記錄了訂單生命週期的每一個狀態，而且每個斷言都直接對應一個業務規則。

3.6　讓轉換函式保持純粹

不管是風格 A 還是風格 B，最好讓轉換方法保持「純粹（pure）」：

  • 給定相同的輸入，永遠回傳相同的輸出
  • 沒有副作用（不修改傳入物件或其他外部狀態，也不呼叫資料庫或外部服務）
// 純粹的轉換：只依賴輸入，回傳確定的輸出
public static Order Pay(Order order, DateTimeOffset paidAt)
{
    return order with
    {
        Status = OrderStatus.Paid,
        PaidAt = paidAt
    };
}

// 不純粹（impure）：直接讀取系統時間
public static Order Pay(Order order)
{
    return order with
    {
        Status = OrderStatus.Paid,
        // 不好：把系統的時間來源寫死在轉換函式裡
        PaidAt = TimeProvider.System.GetUtcNow()
    };
}

純粹的函式極易測試：你只需要提供輸入，驗證輸出，不需要 mock 任何東西。

這種分工常被稱為 functional core, imperative shell：核心邏輯盡量保持「資料進、資料出」的純粹轉換；至於像是讀取時間、存取資料庫、呼叫外部 API、寫入檔案等不穩定的操作，則放在外層負責協調。名字聽起來像架構模式，但實務判斷很簡單：如果一段邏輯可以用普通輸入資料測試，就不要讓它被資料庫、系統時間、或網路呼叫綁住。

如果一個操作確實需要外部依賴，例如讀取當前時間或查詢資料庫，就在 application layer 使用依賴，再把取得的普通資料傳給轉換函式。以時間為例，.NET 內建的 TimeProvider 提供可替換的時間來源；GetUtcNow() 回傳 DateTimeOffset，測試時可以注入受控制的 TimeProvider，不必把系統時間寫死在 domain model 裡：

public sealed class OrderApplicationService(
    IOrderRepository orderRepository,
    TimeProvider timeProvider)
{
    public async Task<Order> PayOrderAsync(string orderId)
    {
        var order = await orderRepository.GetAsync(orderId);

        // 在外層讀取時間，再把普通的值傳給純粹轉換。
        var paidAt = timeProvider.GetUtcNow();
        var paid = OrderWorkflow.Pay(order, paidAt);

        await orderRepository.SaveAsync(paid);
        return paid;
    }
}

轉換函式本身仍然是純粹的，外部依賴由組合層處理。TimeProvider.System 是正式環境使用的系統時間來源；測試則可以注入可控制的實作。

3.7　一個完整的範例

把本章所有概念整合，可以得到一個完整的訂單處理流程。

為了讓重點更清楚，下面先把範例拆成兩段：第一段看 domain model 如何用不可變資料表達狀態轉換；第二段看 application layer 如何協調資料庫、時鐘這類外部依賴。

完整可編譯版本請參考本節後方的原始碼連結。

第一段是 Order record。它保存訂單狀態，也把狀態轉換規則放在 record 內部：

public sealed record Order
{
    public string Id { get; private init; }
    public string CustomerId { get; private init; }
    public OrderStatus Status { get; private init; }
    public ImmutableArray<OrderLine> Lines { get; private init; }
    public decimal Total { get; private init; }
    public DateTimeOffset CreatedAt { get; private init; }
    public DateTimeOffset? SubmittedAt { get; private init; }
    public DateTimeOffset? PaidAt { get; private init; }
    public DateTimeOffset? ShippedAt { get; private init; }
    public string? CancelReason { get; private init; }

    private Order(
        string id,
        string customerId,
        ImmutableArray<OrderLine> lines,
        DateTimeOffset createdAt)
    {
        Id = id;
        CustomerId = customerId;
        Status = OrderStatus.Draft;
        Lines = lines;
        Total = lines.Sum(line => line.Amount);
        CreatedAt = createdAt;
    }

    public static Order CreateDraft(
        string id,
        string customerId,
        ImmutableArray<OrderLine> lines,
        DateTimeOffset createdAt)
    {
        if (lines.IsDefault)
        {
            throw new ArgumentException(
                "訂單項目尚未初始化",
                nameof(lines));
        }

        return new Order(id, customerId, lines, createdAt);
    }

    public Order Submit(DateTimeOffset now)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("只有草稿可以提交");
        if (Lines.IsEmpty)
            throw new InvalidOperationException(
                "訂單必須至少有一個項目才能提交");

        return this with
        {
            Status = OrderStatus.Submitted,
            SubmittedAt = now
        };
    }

    public Order Pay(DateTimeOffset now)
    {
        if (Status != OrderStatus.Submitted)
            throw new InvalidOperationException(
                "只有已提交的訂單可以付款");

        return this with
        {
            Status = OrderStatus.Paid,
            PaidAt = now
        };
    }

    public Order Ship(DateTimeOffset now)
    {
        if (Status != OrderStatus.Paid)
            throw new InvalidOperationException(
                "只有已付款的訂單可以出貨");

        return this with
        {
            Status = OrderStatus.Shipped,
            ShippedAt = now
        };
    }

    public Order Cancel(string reason)
    {
        if (Status is not (
            OrderStatus.Draft or
            OrderStatus.Submitted or
            OrderStatus.Paid))
            throw new InvalidOperationException(
                "只有草稿、已提交、或已付款的訂單可以取消");
        if (string.IsNullOrWhiteSpace(reason))
            throw new ArgumentException(
                "取消訂單必須提供原因",
                nameof(reason));

        return this with
        {
            Status = OrderStatus.Cancelled,
            CancelReason = reason
        };
    }
}

這段程式碼展示的是風格 A：資料和確保自身狀態合法的行為放在一起。建構式和 init 存取子都是 private，所以呼叫方只能透過 CreateDraft、Submit、Pay 等明確的 API 建立狀態。呼叫 Pay 時，它不會修改原本的 Order，而是回傳一個狀態為 Paid 的新版本。

這裡允許 Draft、Submitted、和 Paid 訂單取消，但不允許 Shipped 或 Cancelled 訂單再次取消。Paid 訂單背後還需要自動退款：application service 可以先呼叫純粹的 Cancel，驗證規則並產生尚未儲存的候選版本；如果原訂單是 Paid，接著呼叫付款服務退款，成功後才儲存候選版本。退款如果失敗，就不儲存 Cancelled 版本，資料庫裡的訂單仍維持 Paid。對外應以這個 application service 流程作為取消入口，而不是讓呼叫方自行略過退款。這種外部協調不放進 Order，才能讓 domain transition 保持純粹。

第二段是 application layer。它不負責判斷訂單能不能付款，只負責把外部依賴接起來：

public sealed class OrderApplicationService
{
    private readonly IOrderRepository _repository;
    private readonly TimeProvider _timeProvider;

    public OrderApplicationService(
        IOrderRepository repository,
        TimeProvider timeProvider)
    {
        _repository = repository;
        _timeProvider = timeProvider;
    }

    public async Task<Order> PayAsync(string orderId)
    {
        // 從資料庫讀取當前狀態
        var order = await _repository.GetAsync(orderId);

        // 純粹的狀態轉換（不涉及外部依賴）
        var paid = order.Pay(_timeProvider.GetUtcNow());

        // 儲存新狀態
        await _repository.SaveAsync(paid);

        return paid;
    }
}

原始碼： - DemoOrderTransformationStyleA - DemoOrderTransformationStyleB - DemoOrderTransformationPipeline

這個設計的分層很清楚：

  • Order record 負責資料的定義和狀態轉換規則。
  • OrderApplicationService 負責協調外部依賴（資料庫、時鐘）。
  • 轉換邏輯本身（order.Pay(now)）是純粹的，可以獨立測試。

3.8　常見問題

「每次都建立新物件，效能不會很差嗎？」

對於大多數業務邏輯，這個開銷可以忽略不計。現代 .NET 的 GC 對短命的小物件非常有效率，通常不需要特別優化。此外，record 的 with 執行的是淺層複製，不會深度複製整個物件圖；像 ImmutableArray<T> 這類本身不可變的成員，可以由新舊版本安全共用。因此，建立新版本通常只需要配置新的外層物件。

真正需要注意的是高頻、低延遲的熱路徑（hot path），例如每秒處理數十萬次操作的場景。在這些場景，你應該先測量，找到真正的瓶頸，再決定是否需要優化，而不是預先優化所有程式碼。

我們在第 5 章會討論哪些場景確實不適合不可變設計。

「把所有方法都搬到 OrderWorkflow，這樣好嗎？」

不一定。把行為放在外部是風格 B 的做法，它有它的優缺點。對於業務規則豐富的 domain model，風格 A（行為在 record 內）通常更好，因為比較容易確保狀態合法。

不要為了「資料和行為分離」這個概念而分離——分離應該是因為特定場景有實際的好處，而不是因為某種設計哲學。

3.9　本章回顧

這章討論了「用資料轉換取代原地修改」的核心設計模式。

  • 資料轉換：方法接收舊狀態，回傳新狀態，不修改輸入。這是不可變設計的核心操作。
  • 風格 A（行為在 record 內）和風格 B（行為在外部函式/服務）各有適用場景。不確定時，從風格 A 開始。
  • 業務規則驗證：在轉換方法裡檢查前置條件，可以拋出例外或回傳結果型別。
  • 純粹函式：讓轉換方法不依賴外部狀態，外部依賴由呼叫方在應用程式層注入。
  • 轉換管線：多個轉換步驟可以自然串接，讓業務流程一目了然。

本章為了聚焦資料轉換，仍以單一 Order、OrderStatus enum、和多個 nullable 欄位表達整個生命週期。轉換方法可以在執行期阻止不合法的操作，但風格 B 的公開 positional record 仍不能完整表達「某個狀態必須擁有哪些資料」。

接下來的第 4 章會離開單純的 domain model，討論不可變資料最容易落地的 DTO、command、event 與設定物件。如果 enum、旗標與 nullable 欄位已經讓狀態難以管理，則可以在讀完主線後，再閱讀第 6 章的進階狀態建模。
