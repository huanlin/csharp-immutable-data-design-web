第 2 章　C# records、init 與不可變集合

  • record class 作為不可變資料載體的主要功能

  • 值相等性（value equality）的含義與實務影響

第 1 章介紹了「把改變表達成轉換」的基本思維，以及 record 和 with 運算式的初步用法。這一章要深入探討 C# 提供的不可變資料工具，包括各種 record 語法、init、required，以及如何正確處理集合的不可變性（immutability）。

本章不只說明「這些語法怎麼用」，更重要的是「什麼時候用哪個，以及要注意哪些陷阱」。record struct、readonly record struct 和 FrozenDictionary 也會出現，但它們是用來補完整個不可變資料設計的工具，而不是本章主角。

2.1　record class：不可變參考型別的主力

record class（或簡寫為 record）是本書最常使用的型別。它是一個參考型別，適合用來表示資料快照、DTO（data transfer object、資料傳輸物件）、value object（值物件），以及狀態轉換過程中的中間結果。

record 的價值，在於幫我們消除許多為資料型別反覆撰寫的瑣碎程式碼（boilerplate）。要注意的是，record 本身不會保證「所有東西都不可變」。它提供的是一組很適合不可變設計的語言支援，包括：

  • 配合「位置參數」（positional parameters）語法時，編譯器會產生 init-only 屬性。
  • 自動實作基於值的相等性比較（Equals、GetHashCode、==）。
  • 自動生成 ToString，方便除錯。
  • 支援 with 運算式，用來建立修改後的新版本。

兩種宣告語法

本節介紹兩種 record 寫法：positional record（位置式 record）和 non-positional record（非位置式 record）。後者使用一般的屬性語法宣告，也有人叫它 nominal record；本書後續統一使用「非位置式 record」。

Positional record 的寫法是把主要資料直接寫在型別名稱後方的小括號中，適合屬性少、資料形狀明確的型別：

public record OrderLine(
    string ProductId,
    string ProductName,
    int Quantity,
    decimal UnitPrice
);

編譯器會自動產生建構式（constructor）、init-only 屬性、Deconstruct 方法、相等性比較、和 ToString。

非位置式 record 更接近傳統 class 的寫法，適合需要驗證、預設值或較複雜建構邏輯的型別。以下範例會對 productId、quantity 和 unitPrice 加入驗證：

public sealed record ValidatedOrderLine
{
    public string ProductId { get; private init; }
    public string ProductName { get; private init; }
    public int Quantity { get; private init; }
    public decimal UnitPrice { get; private init; }
    public decimal LineTotal => Quantity * UnitPrice;

    public ValidatedOrderLine(
        string productId,
        string productName,
        int quantity,
        decimal unitPrice)
    {
        if (string.IsNullOrWhiteSpace(productId))
            throw new ArgumentException(
                "ProductId 不能為空", nameof(productId));

        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(
                nameof(quantity), "數量必須大於 0");

        if (unitPrice < 0)
            throw new ArgumentOutOfRangeException(
                nameof(unitPrice), "單價不能為負數");

        ProductId = productId;
        ProductName = productName;
        Quantity = quantity;
        UnitPrice = unitPrice;
    }
}

原始碼： DemoPositionalRecord、DemoNonPositionalRecord

這裡刻意把屬性的 init 存取子設成 private。理由是：這個型別已經把驗證放進建構式，外部程式碼就不應該再透過物件初始設定式（object initializer）覆蓋 Quantity 或 UnitPrice。如果這些屬性的 init 存取子仍是公開的，外部程式便可以在建構式跑完後，透過物件初始設定式覆蓋它們，反而削弱了建構式維護不變條件的效果。

重點整理

Positional record 適合簡單的資料容器，例如 DTO 或不需要複雜驗證的 value object；非位置式 record 適合需要驗證邏輯、預設值或複雜建構流程的型別。

值相等性：record 和 class 的關鍵差異

record 的相等性比較是基於值，而非參考。這和傳統 class 預設比較物件參考的行為不同。請看以下範例：

public record OrderLine(
    string ProductId,
    string ProductName,
    int Quantity,
    decimal UnitPrice
);

var line1 = new OrderLine("P001", "書", 2, 350m);
var line2 = new OrderLine("P001", "書", 2, 350m);

Console.WriteLine(line1 == line2); // True

上面的範例展示了 record 的值相等性：即使 line1 和 line2 是兩個不同的物件，只要它們的屬性值完全相同，相等運算子 == 就會回傳 true。

這在實務上很有用：

  • 在測試中比較兩個 DTO 是否相等，不需要手動逐欄位比較。
  • 把 record 放進 HashSet<T> 或作為 Dictionary<TKey,TValue> 的 key 時，會依照成員值判斷是否相同，行為比較直觀。
  • 可用來比較兩個狀態版本是否真的不同。

考慮值相等性（value equality）時，也要先分清楚「值」和「識別」。Money(100, "TWD") 這類 value object 的語意通常由欄位值決定；兩個金額與幣別相同的物件，可以視為同一個值。相反地，Order、Customer 這類有生命週期的實體，即使某個時間點的欄位內容相同，也不一定代表同一個業務個體。record 讓你不必手寫 Equals、GetHashCode、與相等運算子，就能提供值相等性的比較；但它不會自動替你判斷這個型別是否真的應該用值相等性來表示。

如果要把 record 放進 HashSet<T>，或用作 Dictionary<TKey,TValue> 的 key，還要確保參與相等性與雜湊碼計算的成員不會在放入集合後改變。否則，物件的雜湊碼可能改變，導致集合無法在原本的位置找到它。使用由不可變值組成的 record，可以避開這類問題。

不過，value equality 有一個容易忽略的細節：集合欄位預設仍然依照集合型別自己的相等性規則來處理。如果 record 內含陣列或 IReadOnlyList<T>，預設比較通常不是逐一比較元素內容。這個細節會在本章後面討論集合時進一步說明。

原始碼： DemoValueEquality

2.2　init-only 屬性與 required

init 是 C# 9 引入的屬性存取子（property accessor）。和 set 不同，init 只允許在物件初始化期間設定屬性；物件建立完成後，就不能再修改。

它很適合用在 request DTO 或設定物件：呼叫方可以使用物件初始設定式，型別本身仍然能避免建構後被隨意改寫。

備註：request DTO 通常用來承載外部請求送進系統的資料。例如在 Web API 中，CreateOrderRequest 可以用來接收建立訂單請求送來的 JSON body。

先看一個單純使用 init 的例子：

public class OrderRequest
{
    public string CustomerId { get; init; } = "";
    public string ProductId { get; init; } = "";
}

var request = new OrderRequest
{
    CustomerId = "CUST-42",
    ProductId = "P001"
};

request.CustomerId = "CUST-99"; // 編譯錯誤

init 在語意上比 set 更精確，它的意思是：「這個屬性可以在物件初始化期間設定，但初始化完成後就固定了。」

C# 11 引入的 required 可以搭配 init 使用，強制呼叫方在初始化時設定必要屬性，否則編譯器會報錯：

public class CreateOrderRequest
{
    public required string CustomerId { get; init; }
    public required string ProductId { get; init; }
    public string? Note { get; init; }
}

var request = new CreateOrderRequest
{
    CustomerId = "CUST-100",
    ProductId = "PROD-200",
    Note = "急件處理"
};

var invalidRequest = new CreateOrderRequest
{
    CustomerId = "CUST-100"
}; // 編譯錯誤：少了 ProductId

此範例會出現編譯錯誤 CS9035，因為在建立 invalidRequest 物件的時候沒有初始化必要成員 CreateOrderRequest.ProductId。這比把屬性宣告成 nullable 再到處檢查，更能把資料完整性的要求放在型別設計裡。

不過，required 是編譯期的初始化契約，不是執行期驗證。呼叫方仍然可以把必要成員設定成 null；如果屬性型別是 non-nullable reference type，編譯器通常會提出警告，但 required 本身不會把這種指派變成執行期錯誤。因此，required 不能取代 null 檢查或業務規則驗證。

原始碼： DemoInitRequired

required + init 不能完全取代建構式。當型別需要複雜驗證、計算衍生欄位，或必須維持跨欄位的不變條件時，建構式仍然比較合適。簡單來說：

  • DTO 或設定物件：常用 required + init。
  • 領域型別（domain type，例如 value object 或 entity）：常用建構式集中驗證。
  • 需要防止外部繞過驗證：考慮 private init 或只提供建構式。

例如，required 可以要求呼叫方一定要提供 ProductId 和 Quantity，但不能保證 ProductId 不是空白字串，也不能保證 Quantity 大於 0。這類規則通常適合放在建構式中：

public sealed record OrderItem
{
    public string ProductId { get; }
    public int Quantity { get; }

    public OrderItem(string productId, int quantity)
    {
        // 驗證單一欄位的格式。
        if (string.IsNullOrWhiteSpace(productId))
            throw new ArgumentException(
                "ProductId 不能為空", nameof(productId));

        // 驗證業務規則。
        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        ProductId = productId;
        Quantity = quantity;
    }
}

這類設計會把驗證集中在建構式，並避免呼叫方直接設定尚未驗證的屬性。

2.3　with 運算式：建立修改版本

with 運算式讓你從現有的 record 建立一個新版本，只改指定的欄位，其他欄位沿用原本的值。如以下範例：

var original = new OrderLine("P001", 5);
var updated = original with { Quantity = 10 };

Console.WriteLine(original.Quantity); // 5
Console.WriteLine(updated.Quantity);  // 10

這正是第 1 章「把改變表達成轉換」的寫法。此範例中的 original 訂單項目沒有被修改，updated 則是包含新值的訂單項目。

巢狀更新

當 record 裡面包含另一個 record 時，若要建立一個更新內層資料後的新外層物件，通常會同時寫出外層與內層的 with 運算式，稍嫌冗長：

public record Address(
    string Street,
    string City,
    string PostalCode
);

public record CustomerProfile(
    string Id,
    string Name,
    Address ShippingAddress
);

var profile = new CustomerProfile(
    "C001",
    "王小明",
    new Address("中山路 1 號", "台北市", "10001")
);

var updated = profile with // 建立新的 CustomerProfile
{
    ShippingAddress = profile.ShippingAddress with // 建立新的 Address
    {
        City = "新北市",
        PostalCode = "22001"
    }
};

這裡「冗長」指的是外層的 profile with { ... } 用來建立新的 CustomerProfile，內層又還有 profile.ShippingAddress with { ... } 用來建立新的 Address。寫法雖然比直接指定 profile.ShippingAddress.City 冗長一些，但資料流是明確的：你清楚地知道自己在建立一個新的 ShippingAddress，再把它放進一個新的 CustomerProfile。這比在原地修改更容易追蹤資料流，因為每一次更新都明確表達「從哪個舊值建立哪個新值」。

如果覺得巢狀 with 不容易閱讀，沿用同一個 profile，也可以先把內層的新版本建立出來，再放進外層的新版本：

var newAddress = profile.ShippingAddress with
{
    City = "新北市",
    PostalCode = "22001"
};

var updated = profile with { ShippingAddress = newAddress };

這兩種寫法的資料流相同：先從舊的 ShippingAddress 建立新的 Address，再從舊的 profile 建立新的 CustomerProfile。

如果巢狀層次很深，可以考慮在包住內層資料的型別上定義輔助方法。以上面的例子來說，我們可以在包住 Address 的 CustomerProfile 上提供 WithCity 方法，把更新 ShippingAddress.City 的細節藏在型別內部：

public record CustomerProfile(
    string Id,
    string Name,
    Address ShippingAddress)
{
    public CustomerProfile WithCity(string city)
    {
        return this with
        {
            ShippingAddress = ShippingAddress with { City = city }
        };
    }
}

// 使用起來更清楚
var updated = profile.WithCity("新北市");

第 3 章會深入討論如何把「狀態更新」封裝成「轉換方法」；大型物件圖的巢狀更新問題則會留到第 5 章。這裡要先記住的重點是：with 不是為了讓所有更新都變成一行，而是讓每一次更新都清楚表達「從舊版本建立新版本」。

還要注意，with 可以設定呼叫端有權存取的 init 屬性。如果公開的 init 允許呼叫方組合出不合法的狀態，便需要限制存取層級，或提供目的明確的轉換方法。下一章會以訂單狀態為例，示範如何安排這些轉換方法與業務規則。

原始碼： DemoWithExpression

2.4　淺層不可變的陷阱

這是本章重點之一，也是 C# 開發者最容易踩的坑：

具有 init-only 屬性的 record 提供的是「淺層不可變（shallow immutability）」，不是「深層不可變（deep immutability）」。

來看一個例子：

public record Order(
    string Id,
    List<OrderLine> Lines
);

var order = new Order("ORD-001", new List<OrderLine>());

// 不能替換整個 Lines 參考。
// order.Lines = new List<OrderLine>(); // 編譯錯誤

// 但可以修改 Lines 指向的 List<T> 內容。
order.Lines.Add(new OrderLine("P001", 5)); // 合法

order.Lines 是 init-only 屬性，因此初始化完成後不能重新指向別的集合；但 List<T> 本身仍然是可變集合。init-only 屬性只保護集合參考不能被重新指派，不保護集合內容不能被改。

原始碼： DemoShallowImmutability

改用 IReadOnlyList<T>

比較安全的第一步，是把公開 API 從 List<T> 改成唯讀介面：

public record Order(
    string Id,
    IReadOnlyList<OrderLine> Lines
);

order.Lines.Add(new OrderLine("P001", 5)); // 編譯錯誤!

這可以避免呼叫方透過 order.Lines 直接新增或刪除項目。不過，IReadOnlyList<T> 只是唯讀檢視，不是真正的 immutable collection。

Note: IReadOnlyList<T> 只保證「透過這個介面」不能改變集合結構，例如新增、刪除或重新排序項目；它不保證底層集合不會被其他參考修改，也不保證集合裡的元素物件本身不可變。如果元素是可變的 class，呼叫端仍可取出元素後修改其屬性。簡單來說，結構是唯讀的，而元素本身是否可變，則取決於元素型別。

參閱微軟文件：IReadOnlyList<T> interface

如果外部仍然握有原本的 List<T>，還是可以從那個參考修改集合內容。例如：

public record Order(
    string Id,
    IReadOnlyList<OrderLine> Lines
);

var lines = new List<OrderLine>(); // (1)
var order = new Order("ORD-001", lines); // (2)

Console.WriteLine(order.Lines.Count); // 輸出 0

lines.Add(new OrderLine("P001", 5)); // (3)

Console.WriteLine(order.Lines.Count); // 輸出 1

原始碼： DemoReadOnlyListView

此範例程式碼的閱讀重點：

  1. lines 是外部建立的可變 List<OrderLine>。
  2. order.Lines 和 lines 指向同一個底層集合，只是 order.Lines 只顯露 IReadOnlyList<OrderLine> 介面。
  3. 由於 order.Lines 的型別是 IReadOnlyList<OrderLine>，故無法透過 order.Lines.Add() 來添加元素（無法通過編譯）；但外部仍可透過原本的 lines 參考呼叫 Add 方法。

因此，IReadOnlyList<T> 通常要搭配防禦性複製，或改用真正不可變的集合型別。下一節會整理這些選擇。

2.5　不可變集合的選擇指南

處理集合時，先問一個問題：你要防止的是「呼叫方修改集合」，還是「資料結構本身在任何地方都不能被修改」？

如果只是要保護 API 輸入輸出或 DTO，可以把防禦性複製再包成唯讀檢視：

public sealed class SafeOrder
{
    public string Id { get; }
    public IReadOnlyList<OrderLine> Lines { get; }

    public SafeOrder(string id, IEnumerable<OrderLine> lines)
    {
        ArgumentNullException.ThrowIfNull(lines);
        Id = id;
        Lines = Array.AsReadOnly(lines.ToArray());
    }
}

這裡刻意使用一般的 class，因為範例要示範的是集合封裝，而不是 record 的值相等性。lines.ToArray() 先建立新的陣列，切斷與外部可變集合的聯繫；Array.AsReadOnly 再包住這份陣列，避免呼叫方把公開的 IReadOnlyList<T> 轉回陣列後修改項目。

這仍然只是集合結構的保護。如果元素是可變物件，呼叫方取出元素後仍可能修改其狀態；因此，集合元素本身也應該採用合適的不可變型別。如果需要能夠建立新版本的不可變資料結構，可以改用 System.Collections.Immutable 家族的 ImmutableList：

var productIds = ImmutableList.Create("P001", "P002");

var updatedProductIds = productIds.Add("P003");

Console.WriteLine(productIds.Count);        // 輸出 2
Console.WriteLine(updatedProductIds.Count); // 輸出 3

由此範例可知，ImmutableList 的 Add 方法不會修改原本的集合（此範例的 productIds），而是回傳包含新項目的集合版本。這是 ImmutableList<T> 和 List<T> 在語意上最大的差異。

以下表格整理了幾種集合類型的適用場景，其中 ImmutableArray<T>、ImmutableList<T> 和 ImmutableDictionary<TKey, TValue> 屬於 System.Collections.Immutable 家族，FrozenDictionary<TKey, TValue> 則位於 System.Collections.Frozen。

場景 建議
小型 DTO，只需保護公開 API IReadOnlyList<T> + 防禦性複製與唯讀包裝
建立後很少修改，以讀取為主 ImmutableArray<T>
需要頻繁新增、刪除，且保留多個版本 ImmutableList<T>
key-value 狀態表，需要不可變更新 ImmutableDictionary<TKey, TValue>
啟動時建立一次，之後大量查詢 FrozenDictionary<TKey, TValue>

IReadOnlyList<T> 是「介面上的唯讀」；ImmutableArray<T>、ImmutableList<T> 和 ImmutableDictionary<TKey, TValue> 是「資料結構本身不可變」，但適合的更新模式不同；FrozenDictionary<TKey, TValue> 則是建立後固定、為大量查詢最佳化的集合。

這些集合類型各有不同的設計目的，不要一看到 immutable design 就全部換成 ImmutableList<T>。

ImmutableArray<T> 的 default 陷阱

ImmutableArray<T> 是 struct。當它處於未初始化狀態，例如指派為 default，它內部包住的陣列其實是 null：

ImmutableArray<OrderLine> items = default; // 小心陷阱!

Console.WriteLine(items.IsDefault); // True

try
{
    int length = items.Length; // 拋出 NullReferenceException
}
catch (NullReferenceException)
{
    Console.WriteLine("items 尚未初始化。");
}

var safeItems = ImmutableArray<OrderLine>.Empty; // 推薦寫法

所以使用 ImmutableArray<T> 時，請明確初始化為 ImmutableArray<T>.Empty，或在使用前檢查 IsDefault 屬性。不要把 default 當成空集合（empty collection）；它代表的是未初始化狀態。

原始碼： DemoReadOnlyCollections

集合欄位與值相等性

Record 的值相等性（value equality）對集合欄位有一個容易忽略的細節：兩個 record 即使集合內容相同，只要集合物件不是同一個，預設相等性比較就可能回傳 false。請看以下範例：

public record Order(
    string Id,
    IReadOnlyList<OrderLine> Lines
);

var lines = new[] { new OrderLine("P001", 5) };

var a = new Order("ORD-001", lines);
var b = new Order("ORD-001", lines.ToArray());

Console.WriteLine(a == b); // False

閱讀上方範例時，請留意 a 和 b 的 Lines 內容相同，但來自不同的陣列物件，因此 a == b 的結果是 false。如果你的設計需要「集合內容也參與相等性比較」，不能只依賴 record 的預設相等性。 請在比較時明確使用 SequenceEqual，或自行覆寫 Equals 和 GetHashCode 方法。

原始碼： DemoCollectionValueEquality

Note

ImmutableArray<T> 雖然實作了 IStructuralEquatable 介面，但一般呼叫 Equals 或使用 == 時，並不會逐一比較元素內容，而是比較底層陣列的參考。若要逐一比較元素，請明確使用 SequenceEqual。

從資料生命週期看 FrozenDictionary

FrozenDictionary<TKey,TValue> 的適用場景是：啟動或初始化時建立一次，之後只做大量查詢，完全不修改。

例如電商系統常會有「商品分類代碼對應顯示名稱」、「付款方式代碼對應處理規則」、「國家代碼對應出貨區域」這類對照表。這些資料通常在啟動時從設定檔或資料庫載入，之後會在訂單建立、結帳流程與查詢畫面中反覆查詢，但不會在每次查詢時被修改。這時候，可以先準備好不再修改的 key 和 value，再建立 FrozenDictionary 作為查詢索引：

using System.Collections.Frozen;

var categoryNames = new Dictionary<string, string>
{
    ["BOOK"] = "書籍",
    ["SOFTWARE"] = "軟體"
}.ToFrozenDictionary();

Console.WriteLine(categoryNames["BOOK"]); // 輸出：書籍

ToFrozenDictionary 的建立成本相對高，但建立完成後能提供快速的查詢。它適合「很少建立、經常讀取」的資料，不適合每次更新都建立新版本的狀態表。

原始碼： DemoFrozenDictionary

這個案例的重點不是「不可變一定比較快」，而是不可變設計迫使我們釐清資料生命週期：哪些資料只在初始化階段改變？哪些資料進入查詢階段後就應該固定？當生命週期劃分清楚，就能選擇更貼合用途的資料結構。

如果後台真的需要修改商品分類或出貨區域，通常也是更新資料來源後重新載入快取，而不是直接修改已建立的查詢索引。換句話說，集合選型不是語法偏好，而是資料生命週期的設計決策。

2.6　record struct 與 readonly record struct

record struct 是 C# 10 引入的型別。它是實值型別（value type），但仍保留 record 的 value equality、ToString 和 with 支援。要注意的是，語法相近的 record class 是參考型別（reference type）。

以下是一個 record struct 範例：

public readonly record struct Money(decimal Amount, string Currency);

var price = new Money(1200m, "TWD");
var discounted = price with { Amount = 960m };

談到 struct 時，常見的簡化說法是「struct 在 stack、class 在 heap」。這個說法不夠精確：實值型別可能出現在區域變數、物件欄位、陣列元素，boxing 時也會進入 heap。因此，選擇 record struct 時，不要只考慮 stack/heap，而要看它在語意上是不是一個值、實例大小與複製成本是否足夠低，以及是否會頻繁 boxing。

什麼時候使用 record struct？

record struct 適合以下情況：

  • 實例很小；常見經驗值是 16 bytes 左右或更小，但仍應依實際使用方式評估。
  • 語意上是一個「值」，例如金額、座標、時間區間。
  • 不需要繼承。
  • 不會頻繁 boxing。
  • 大量建立或內嵌在其他物件中時，希望降低 heap 配置。

不適合的情況：

  • 實例很大，複製成本會變高。
  • 包含複雜參考型別欄位，使值語意變得模糊。
  • 需要繼承或追蹤長生命週期身分。

record struct 本身不能是 null，但可以使用 nullable value type，例如 Money?，來表示有值或缺值。如果型別在大多數使用情境都需要處理 null，則應重新評估參考型別是否更自然。

record struct 預設是可變的

一個容易混淆的地方是：使用位置式（positional）宣告的 record class 產生的是 init-only 屬性，但位置式 record struct 產生的是可讀寫屬性。

範例：

// record struct 預設可變
public record struct Point(double X, double Y);

var p = new Point(1.0, 2.0);
p.X = 5.0; // 修改成員是合法的

如果你要的是不可變的值型別，請明確寫成 readonly record struct：

public readonly record struct Point(double X, double Y);

var p = new Point(1.0, 2.0);
p.X = 5.0; // 編譯錯誤

readonly 讓編譯器要求結構的實例狀態不可被修改，也能減少某些唯讀路徑上的防禦性複製（defensive copy）風險。如果非唯讀 struct 很大，又在高頻路徑中被反覆複製，應該用 profiler 確認實際成本，再決定是否需要調整。

避免可變 struct

可變 struct 的行為很容易產生誤解：程式看起來能修改原值，實際上卻可能只改到複本。以下範例中，陣列元素可以被原地修改，但透過 IList<T> 介面索引子取出的值，只是暫時複本：

using System.Collections.Generic;

var array = new MutableCounter[] { new() };
array[0].Increment();
Console.WriteLine(array[0].Value); // 輸出：1

IList<MutableCounter> list = new List<MutableCounter> { new() };

// 透過 IList<T> 索引子取出的值是複本
list[0].Increment();  // [A] 這裡只改動了取出的複本
Console.WriteLine(list[0].Value); // 輸出：0

public struct MutableCounter
{
    public int Value;

    public void Increment()
    {
        Value++;
    }
}

註解標記 [A] 的程式碼修改的是複本，修改完就遺失了。因此，清單中的元素仍然是原本的值。為了避開這類難以除錯的行為，本書建議：如果要設計實值型別，優先使用不可變的 readonly record struct。

原始碼： DemoRecordStruct

2.7　本章回顧

這章介紹了 C# 中用來建構不可變資料的主要語言特性：

  • record class 是本書最常使用的不可變資料載體，提供 value equality、ToString 和 with 運算式。
  • Positional record 適合簡單資料容器；非位置式 record 適合需要驗證與建構邏輯的型別。
  • init 讓屬性只能在初始化期間設定；required 強制呼叫方提供必要資料。
  • with 運算式 從現有 record 建立帶有修改的新版本。
  • record struct 是實值型別版本，預設可變；若要不可變值型別，優先使用 readonly record struct。
  • 具有 init-only 屬性的 record 提供的是淺層不可變：集合屬性的型別要特別注意，List<T> 配合 record 不能提供真正的不可變性。
  • 不可變集合的選擇：IReadOnlyList<T> 配合防禦性複製與唯讀包裝，適合多數 API 輸入輸出；ImmutableArray<T> 適合讀取為主；ImmutableList<T> 與 ImmutableDictionary<TKey,TValue> 適合需要不可變更新的集合；FrozenDictionary<TKey,TValue> 適合建立後大量查詢。

到這裡，我們解決的是「如何表示與複製不可變資料」。不過，record、init、和 with 不會自動決定業務轉換應該放在哪裡，也不會自動保證每個狀態都合法。

下一章是全書的核心章節，我們會深入討論「用資料轉換取代原地修改」的設計模式，以及如何判斷把行為放在 record 內部還是外部服務更合適。
